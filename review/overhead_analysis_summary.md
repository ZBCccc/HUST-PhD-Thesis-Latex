# VQNomos 开销分析总结

本文档整合了VQNomos相比Nomos在各维度的开销分析，包括客户端存储、服务器存储、通信开销的理论分析与实例化计算。

## 1. 参数设置

### 1.1 密码学原语实例化

| 参数 | 含义 | 字节数 | 来源 |
|------|------|--------|------|
| $\|\mathbb{G}\|$ | 群元素（压缩椭圆曲线点） | 33 B | BN254曲线压缩点 |
| $\lambda$ | 哈希值长度 | 32 B | SHA-256输出 |
| $\|\sigma\|$ | 签名长度 | 64 B | Ed25519签名 |
| $t$ | 版本号 | 8 B | uint64_t |

### 1.2 协议参数

| 参数 | 含义 | 值 | 来源 |
|------|------|-----|------|
| $\ell$ | RBF插入侧展开次数 | 3 | `Nomos/src/vq-nomos/Gatekeeper.cpp:315` |
| $k$ | 查询侧采样参数 | 2 | `Nomos/src/vq-nomos/Client.cpp:152` |
| $M$ | XSet位数组大小 | $2^{22}$ | 第四章默认参数 |
| $b_{\text{cnt}}$ | 更新计数器大小 | 4 B | uint32_t |

### 1.3 数据集参数

| 数据集 | 不同关键词数 $\|\mathcal{W}\|$ | 总关系数 $N$ |
|--------|------------------------------|-------------|
| Crime | 63,659 | 7,989,987 |
| Enron | 16,241 | 5,190,199 |
| Wiki | 10,000 | 4,565,948 |

## 2. 客户端存储开销

### 2.1 理论公式

**Nomos**：
```
S_client^Nomos = L_W + |W| · b_cnt
```

**VQNomos**：
```
S_client^VQNomos = L_W + |W| · b_cnt + b_anchor
```

**增量**：
```
ΔS_client = b_anchor = 104 B
```

其中：
- $L_W$：关键词字符串总字节数
- $b_{\text{anchor}} = 8 + 32 + 64 = 104$ B（版本号 + 根哈希 + 签名）

### 2.2 实例化结果

| 数据集 | Nomos 计数器部分 | VQNomos 计数器+锚点部分 | 增量 |
|--------|-----------------|----------------------|------|
| Crime | 254,636 B (248.67 KB) | 254,740 B (248.77 KB) | 104 B |
| Enron | 64,964 B (63.44 KB) | 65,068 B (63.54 KB) | 104 B |
| Wiki | 40,000 B (39.06 KB) | 40,104 B (39.16 KB) | 104 B |

**结论**：VQNomos的客户端存储增量为常数级（104 B），相对增量可忽略不计。

## 3. 服务器存储开销

### 3.1 理论公式

**Nomos**：
```
S_server^Nomos = N × 97 + M/8 B
```

**VQNomos**：
```
S_server^VQNomos = N × 97 + M/8 + 64M + N × ℓ × 132 + 64Nℓ B
                  ≈ 64M + 196Nℓ B
```

**增量**：
```
ΔS_server ≈ 64M + (196ℓ - 97)N B
```

### 3.2 组件分解

| 组件 | Nomos | VQNomos | 说明 |
|------|-------|---------|------|
| TSet | $N × 97$ B | $N × 97$ B | 主项索引 |
| XSet | $M/8$ B | $M/8$ B | Bloom Filter位数组 |
| QTree | - | $64M$ B | XSet的Merkle Hash Tree |
| MPos | - | $N × \ell × 132$ B | 交叉标签位置映射 |
| MTree | - | $64N\ell$ B | 每条关系的Merkle树 |

### 3.3 实例化结果（$\ell=3$, $M=6N$）

**单位关系开销**：
- Nomos：$97.75$ B/关系
- VQNomos：$972$ B/关系
- 增量：$874.25$ B/关系（约9.95倍）

**具体数据集**（理论预测）：

| 数据集 | $N$ | Nomos | VQNomos | 增量倍数 |
|--------|-----|-------|---------|---------|
| Crime | 7,989,987 | 765 MB | 7.4 GB | 9.95× |
| Enron | 5,190,199 | 497 MB | 4.8 GB | 9.95× |
| Wiki | 4,565,948 | 437 MB | 4.2 GB | 9.95× |

**增量分解**（以Crime为例）：

| 组件 | 大小 | 占比 |
|------|------|------|
| QTree | 2.9 GB | 42.7% |
| MPos | 3.1 GB | 45.1% |
| MTree | 1.5 GB | 22.0% |
| **总增量** | **6.8 GB** | **100%** |

**结论**：VQNomos的服务器存储增量约为9.95倍，主要来自MPos（45.1%）和QTree（42.7%）。

## 4. 通信开销

### 4.1 理论公式

#### 4.1.1 客户端上传

**Nomos**：
```
C_client^Nomos = m × 33 + m(n-1)k × 33 + |env|
                ≈ 33m(2n - 1) B
```

**VQNomos**：
```
C_client^VQNomos = C_client^Nomos + 8 + 4k
                  = 33m(2n - 1) + 16 B
```

**增量**：
```
ΔC_client = 16 B（常数）
```

#### 4.1.2 服务器下载

**Nomos**：
```
C_server^Nomos = 41m B
```

**VQNomos**：
```
C_server^VQNomos = 41m + 104 + (N_+ × 2 + N_-) × 704 + m(n-1) × 298 B
```

最坏情况（$N_+ = m(n-1)$, $N_- = 0$）：
```
C_server^VQNomos = 41m + 104 + m(n-1) × 1706 B
```

**增量**：
```
ΔC_server = 104 + m(n-1) × 1706 B
```

### 4.2 实例化结果（$m=100$, $n=2$）

#### 4.2.1 客户端上传

| 方案 | 大小 | 增量 | 增量比例 |
|------|------|------|---------|
| Nomos | 9,900 B (9.67 KB) | - | - |
| VQNomos | 9,916 B (9.68 KB) | 16 B | 0.16% |

#### 4.2.2 服务器下载

| 方案 | 大小 | 增量 | 增量倍数 |
|------|------|------|---------|
| Nomos | 4,100 B (4.00 KB) | - | - |
| VQNomos | 174,804 B (170.7 KB) | 170,704 B | 42.6× |

**VQNomos增量分解**：

| 组件 | 大小 | 占比 |
|------|------|------|
| 版本锚点 | 104 B | 0.06% |
| QTree路径 | 140,800 B | 82.5% |
| Merkle-Open | 29,800 B | 17.5% |
| **总增量** | **170,704 B** | **100%** |

#### 4.2.3 总通信开销

| 方案 | 大小 | 增量 | 增量倍数 |
|------|------|------|---------|
| Nomos | 14,000 B (13.67 KB) | - | - |
| VQNomos | 184,720 B (180.4 KB) | 170,720 B | 13.2× |

**结论**：
1. VQNomos的客户端上传增量可忽略不计（0.16%）
2. VQNomos的服务器下载增量显著（42.6倍），主要来自QTree认证路径（82.5%）
3. VQNomos的总通信开销增量约为13.2倍

### 4.3 参数敏感性

#### 4.3.1 关于 $m$ 的依赖

| 方案 | 客户端上传 | 服务器下载 | 总计 |
|------|-----------|-----------|------|
| Nomos | $O(m × n)$ | $O(m)$ | $O(m × n)$ |
| VQNomos | $O(m × n)$ | $O(m × n × \log M)$ | $O(m × n × \log M)$ |

#### 4.3.2 关于 $n$ 的依赖

| 方案 | 客户端上传 | 服务器下载 | 总计 |
|------|-----------|-----------|------|
| Nomos | $O(m × n)$ | $O(m)$ | $O(m × n)$ |
| VQNomos | $O(m × n)$ | $O(m × n × \log M)$ | $O(m × n × \log M)$ |

#### 4.3.3 关于 $k$ 的依赖

| 方案 | 客户端上传 | 服务器下载 | 总计 |
|------|-----------|-----------|------|
| Nomos | $O(m × n × k)$ | $O(m)$ | $O(m × n × k)$ |
| VQNomos | $O(m × n × k)$ | $O(m × n × k × \log M)$ | $O(m × n × k × \log M)$ |

**说明**：增大$k$会显著增加VQNomos的服务器下载开销，但不影响Nomos。

## 5. 综合对比

### 5.1 开销维度总览

| 开销维度 | Nomos | VQNomos | 增量 | 增量性质 |
|---------|-------|---------|------|---------|
| 客户端存储 | $L_W + \|\mathcal{W}\| × 4$ B | $L_W + \|\mathcal{W}\| × 4 + 104$ B | 104 B | 常数级 |
| 服务器存储 | $97.75N$ B | $972N$ B | $874.25N$ B | 9.95倍 |
| 客户端上传 | $33m(2n-1)$ B | $33m(2n-1) + 16$ B | 16 B | 常数级 |
| 服务器下载 | $41m$ B | $41m + m(n-1) × 1706$ B | $m(n-1) × 1706$ B | 42.6倍 |
| 总通信 | $m(66n+8)$ B | $m(66n+8) + m(n-1) × 1706$ B | $m(n-1) × 1706$ B | 13.2倍 |

### 5.2 关键观察

1. **客户端开销**：VQNomos的客户端存储和上传增量都是常数级，可忽略不计

2. **服务器存储**：VQNomos的服务器存储增量约为9.95倍，主要来自：
   - MPos（45.1%）：为每个交叉标签记录位置与根认证
   - QTree（42.7%）：为XSet构建全局Merkle Hash Tree
   - MTree（22.0%）：为每条关系维护Merkle树

3. **服务器下载**：VQNomos的服务器下载增量约为42.6倍，主要来自：
   - QTree路径（82.5%）：每条路径704字节
   - Merkle-Open（17.5%）：每个关系298字节

4. **总通信**：VQNomos的总通信增量约为13.2倍，由服务器下载主导

### 5.3 渐近复杂度对比

| 开销维度 | Nomos | VQNomos | 增量来源 |
|---------|-------|---------|---------|
| 更新计算 | $O(\ell)$ | $O(\ell\log M)$ | QTree更新 |
| 搜索计算（服务器） | $O(m × k(n-1))$ | $O(m(n-1)(k\log M + \ell))$ | QTree查询 + Merkle-Open |
| 验证计算（客户端） | - | $O(m(n-1)(k\log M + \ell))$ | 从零引入 |
| 通信开销 | $O(m × k(n-1))$ | $O(m(n-1)(k\log M + \ell\|\mathbb{G}\|))$ | 证明材料 |
| 服务器存储 | $O(N\ell + M)$ | $O(N(\ell + \lambda) + M\lambda)$ | QTree + MPos + MTree |

## 6. 可直接写入第四章的综合表述

> 综合开销分析表明，VQNomos在引入可验证性的同时，在不同维度产生了不同程度的开销增量。在客户端侧，VQNomos仅需额外维护一个104字节的版本锚点，存储增量为常数级；在搜索阶段，客户端上传仅增加16字节（版本号与采样索引），增量可忽略不计。在服务器侧，VQNomos的存储开销约为Nomos的9.95倍，主要来自MPos（45.1%）、QTree（42.7%）与MTree（22.0%）三类辅助结构；在搜索阶段，服务器下载开销约为Nomos的42.6倍，主要来自QTree认证路径（82.5%）与Merkle-Open选择性开封材料（17.5%）。总体而言，VQNomos的开销增量主要集中在服务器侧，而客户端侧的增量可忽略不计，这与可验证动态对称可搜索加密的设计目标相符：将验证负担从客户端转移到服务器，同时保持客户端的轻量级特性。

## 7. 优化方向

### 7.1 减小 $k$（采样参数）

**影响**：
- 客户端上传：减少50%（$k=2 \to k=1$）
- 服务器下载（QTree）：减少50%
- 服务器下载（Merkle-Open）：减少50%

**代价**：
- 降低采样覆盖率
- 可能影响安全性

### 7.2 减小 $M$（XSet大小）

**影响**：
- QTree路径长度：$\log_2 M$ 减小
- 例如 $M=2^{20}$：路径长度减少64 B（减少9.1%）

**代价**：
- 增加Bloom Filter误判率
- 影响查询准确性

### 7.3 压缩Merkle路径

**方法**：
- 使用路径压缩（只传输必要节点）
- 使用批量验证（共享公共前缀）

**潜在节省**：
- 对于多个关系，可共享QTree路径的公共前缀
- 理论节省：10-30%

### 7.4 增量更新

**方法**：
- 客户端缓存上一次查询的QTree根
- 只传输变化的路径节点

**潜在节省**：
- 对于频繁查询同一关键词的场景
- 理论节省：50-80%

### 7.5 服务器存储优化

**方法**：
- QTree使用增量存储（只存储变化的节点）
- MTree共享公共子树
- MPos使用更紧凑的数据结构

**潜在节省**：
- 实际节省取决于更新模式
- 理论节省：20-40%
