## 1. Overall Judgment

**章节目的**：针对第二章 $\Pi_{\mathsf{VQ}}$ 机制在 OPRF 盲化架构下暴露的地址替换攻击漏洞，提出基于 Merkle 选择性开封的轻量级地址绑定机制，将"地址归属正确"的隐式前提转化为可独立验证的密码学对象。

**就绪度**：Revision-needed

**最严重的技术问题**：命题 3.1 的证明在 $G_2$ 分析中声称 $p_2=0$，但 True Negative 分支（$\mathsf{Auth}_{i,j}=\emptyset$）下客户端跳过子集检查，此时对手的胜利条件 $\mathsf{Verify}'=1 \land \mathsf{ProofAddr}_{i,j}\not\subseteq\mathcal{A}_{i,j}^{(Q)}$ 可同时被满足，$p_2=0$ 的结论不成立。这是一个真实的证明缺口。

## 2. Issue List

### Critical

**C1. [Proof Gap] 命题 3.1 证明中 $p_2=0$ 的结论存在缺口——True Negative 分支未被封堵**

- **位置**：§3.3.1，命题 3.1 证明，"$G_2$ 中的胜利概率分析"段落
- **问题**：证明声称在 $G_2$ 中 $p_2=0$，理由是"只要客户端输出 Accept，就绝对有 $\mathsf{ProofAddr}_{i,j}\subseteq\mathcal{A}_{i,j}^{\mathsf{open}}=\mathcal{A}_{i,j}^{(Q)}$ 恒成立"。但该论证遗漏了 True Negative 分支：当 $\mathsf{Auth}_{i,j}=\emptyset$ 时，算法 4 第 26-27 行直接跳过子集检查，$\mathcal{A}_{i,j}^{\mathsf{open}}=\emptyset$。此时恶意服务器可以：(1) 对一个实际存在的关系故意不返回 $\mathsf{Auth}_{i,j}$；(2) 在 $\mathsf{QTree}$ 证明中使用集合外地址；(3) 客户端跳过归属检查后仍通过 $\mathsf{VfPath}$ 验证。此时 $\mathsf{Verify}'=1$ 与 $\mathsf{ProofAddr}_{i,j}\not\subseteq\mathcal{A}_{i,j}^{(Q)}$ 可同时成立，对手胜利条件被满足，$p_2\neq 0$。
- **修改建议**：需要在证明中显式处理 True Negative 分支。有两种修复路径：(a) 在定义 3.1 的安全实验中增加前提条件，限定胜利条件仅考虑 $\mathsf{Auth}_{i,j}\neq\emptyset$ 的关系；(b) 修改算法 4 的验证逻辑，当服务器对某个关系声明 Negative 但未提供 Auth 时，客户端需要额外的机制（如令牌侧的存在性证明）来区分"关系确实不存在"与"服务器恶意隐匿 Auth"。无论哪种路径，都需要在证明中补充对应的论证。

**C2. [Notation] 跨章节符号体系严重不一致**

- **位置**：全章，与第二章 bf.tex 对比
- **问题**：第二章与第三章对同一概念使用了完全不同的下标体系：
  - 关系域：第二章 $\mathcal{R}(Q)=\{(j,\mathsf{id})\}$，第三章 $\mathcal{R}_{\mathsf{entry}}(Q)=\{(i,j)\}$
  - 关键词索引：第二章用 $j$，第三章用 $i$
  - 条目/文件索引：第二章用 $\mathsf{id}$，第三章用 $j$
  - 采样地址集合：第二章 $\mathcal{A}_{j,\mathsf{id}}^{(t,\nu)}$，第三章 $\mathcal{A}_{i,j}^{(Q)}$
  - 证明地址：第二章 $\mathsf{ProofAddr}_{j,\mathsf{id}}$，第三章 $\mathsf{ProofAddr}_{i,j}$

  这使得两章的安全定义无法直接对接。特别是命题 3.2（组合可验证性）试图将两章的结论组合，但两章使用的符号体系不兼容，读者无法确认 $\Pr[E_{\mathsf{bit}}]$ 中引用的第二章命题是否适用于第三章的符号语境。
- **修改建议**：统一两章的下标体系。建议第三章沿用第二章的 $(j,\mathsf{id})$ 约定，或在第三章开头给出显式的符号映射表，并在命题 3.2 的证明中明确说明符号对应关系。

**C3. [Definition] 定义 3.1 的安全实验形式化不充分**

- **位置**：§3.1.2，定义 3.1
- **问题**：
  1. 对手模型不明确：未显式说明对手控制的是服务器还是网关，也未说明对手是否可以观察到诚实方的内部状态。从上下文推断对手应扮演恶意服务器，但定义中未写明。
  2. $\mathsf{Verify}'$ 未在定义时给出形式化规范——算法 4 在定义之后才出现。定义应当自包含或至少前向引用。
  3. $\mathcal{A}_{i,j}^{(Q^*)}$ 的计算方式未在实验中明确：采样位置 $\{\beta_t\}$ 由谁决定？是挑战者在 GenToken 时确定的，还是对手可以影响的？
  4. 实验未说明 $\mathsf{MSet}$ 的初始化与维护由谁执行——如果由对手（恶意服务器）维护，则对手可以任意篡改 $\mathsf{MSet}$，这与算法描述中"服务器本地维护"的设定一致，但需要在实验中显式声明。
- **修改建议**：重写安全实验，显式指定：(a) 对手角色（恶意服务器）；(b) 挑战者诚实执行的算法范围（Setup、Update 中的网关侧、GenToken）；(c) 对手控制的状态（服务器侧所有状态，包括 $\mathsf{MSet}$）；(d) $\mathcal{A}_{i,j}^{(Q^*)}$ 的精确计算规则。

### Major

**M1. [Proof Gap] 命题 3.2（组合可验证性）的事件分解未论证穷尽性**

- **位置**：§3.3.1，命题 3.2 证明
- **问题**：证明将对手成功分解为 $E_{\mathsf{addr}}$（地址替换）和 $E_{\mathsf{bit}}$（位值伪造）两个事件，并声称"客户端在组合语义下接受错误结果，必定且仅可能由这两类事件之一引发"。但该穷尽性声明未经论证。至少还存在以下攻击向量未被覆盖：
  - 版本回滚攻击（服务器返回旧版本的 QTree 状态）
  - 候选枚举截断攻击（服务器在 TSet 阶段漏返回候选）
  - 语义重算错误（$\mathsf{Res}'$ 的重算逻辑本身是否可被欺骗）

  虽然版本回滚由第二章的版本一致性命题处理，候选枚举由其他机制保障，但证明中应当显式说明这些攻击向量为何不在 $\mathsf{Adv}^{\mathsf{CV}}$ 的范围内，或者为何已被其他组件覆盖。
- **修改建议**：在证明中补充穷尽性论证，明确说明 $E_{\mathsf{addr}} \cup E_{\mathsf{bit}}$ 覆盖了所有导致 $\mathsf{Res}' \neq \mathsf{Res}_{\mathsf{true}}$ 的攻击路径，或者在 $\mathsf{Adv}^{\mathsf{CV}}$ 的定义中精确界定其保护范围。

**M2. [Definition] $\mathsf{Adv}^{\mathsf{CV}}$ 缺少形式化安全实验**

- **位置**：§3.3.1，命题 3.2
- **问题**：命题 3.2 引入了 $\mathsf{Adv}_{\Pi,\mathcal{A}}^{\mathsf{CV}}(\lambda)$，但仅给出了自然语言描述（"客户端输出 Accept，但其接受的结果集合 $\mathsf{Res}'$ 与真实资格语义发生偏离的概率"）。没有对应的形式化安全实验 $\mathsf{Exp}^{\mathsf{CV}}$。"真实资格语义"是什么？是基于当前版本 $t$ 的语义，还是基于最新版本的语义？偏离的度量是什么——$\mathsf{Res}' \neq \mathsf{Res}$（服务器声明的结果）还是 $\mathsf{Res}' \neq \mathsf{Res}_{\mathsf{true}}$（真实结果）？
- **修改建议**：在命题 3.2 之前补充 $\mathsf{Exp}^{\mathsf{CV}}$ 的形式化定义，明确实验流程、对手能力、胜利条件中"真实资格语义"的精确含义。

**M3. [Reduction] 命题 3.1 证明中 $\mathcal{B}_2$ 的归约细节不完整**

- **位置**：§3.3.1，命题 3.1 证明，Game $G_2$ 段落
- **问题**：归约算法 $\mathcal{B}_2$ 的描述过于简略。按照 CLAUDE.md 的要求，每个归约算法必须显式说明：(a) 持有哪些密钥；(b) 缺少哪个组件并由预言机/挑战替代；(c) 如何模拟完整交互；(d) 不可区分性损失在哪里产生。当前证明仅说"$\mathcal{B}_2$ 仅需将伪造路径 $\pi^*$ 与真实树路径进行逐层回溯比对，必定能在首个分歧节点处提取出一对哈希碰撞"，但未说明 $\mathcal{B}_2$ 如何获取真实树路径（它需要维护所有 Merkle 树的完整状态），也未说明 $\mathcal{B}_2$ 如何模拟对手的 Update 和 GenToken 查询。
- **修改建议**：补充 $\mathcal{B}_2$ 的完整构造：(a) $\mathcal{B}_2$ 接收 CR 挑战中的哈希函数 $H_m$；(b) 本地诚实采样所有密钥并维护完整状态（包括所有 Merkle 树）；(c) 当 $E_2$ 发生时，利用本地维护的真实树与对手提交的伪造路径进行逐层比对，提取碰撞对。

**M4. [Logic] 签名绑定 $I(w)$ 而非 $w$ 本身——桶碰撞风险未讨论**

- **位置**：§3.1.3，"完整集合的根认证"段落，公式 (3.5)
- **问题**：签名消息为 $I(w)\|\mathsf{rt}$，其中 $I(\cdot)$ 是关键词到桶索引的映射。文中强调该绑定防止了"跨关键词的根认证对象重放攻击"。但 $I(\cdot)$ 通常不是单射——不同关键词可能映射到同一桶索引 $I(w)=I(w')$。在此情况下，关键词 $w$ 的根认证对象可被合法地用于关键词 $w'$（只要 $I(w)=I(w')$），签名验证仍会通过。该桶碰撞场景下的安全影响未被讨论。
- **修改建议**：(a) 分析桶碰撞对地址绑定健全性的影响——如果 $I(w)=I(w')$ 但 $w \neq w'$，跨关键词根重放是否构成有效攻击？(b) 如果构成威胁，考虑将签名消息改为 $H(w)\|\mathsf{rt}$（使用抗碰撞哈希而非桶索引）；(c) 如果不构成威胁（例如因为 Merkle 树的叶子内容本身绑定了关键词），需要在文中显式论证。

**M5. [Leakage] 隐私性边界声明 (3.12) 缺乏形式化论证**

- **位置**：§3.3.2，公式 (3.12)
- **问题**：文中声称 $\mathcal{L}_{\mathsf{Search}}^{\mathsf{MO},\mathcal{S}}(Q)=\mathcal{L}_{\mathsf{Search}}^{\mathsf{VQ},\mathcal{S}}(Q)$，理由是"Merkle-open 机制未向半诚实服务器暴露任何新鲜信息"。但这仅是直觉论证，不是形式化证明。具体而言：
  - $\mathsf{MPos}$ 的键空间与 $\mathsf{XSet}$ 相同，但 $\mathsf{MPos}$ 的值空间包含位置索引 $r$ 和根 $\mathsf{rt}$——这些是否构成新的泄露？
  - $\mathsf{MTree}$ 存储了完整的 Merkle 树内部节点——这些哈希值是否可被服务器用于推断关键词间的关联？
  - 搜索阶段服务器查询 $\mathsf{MPos}$ 的命中/未命中模式是否泄露了额外的交叉匹配信息？

  按照 CLAUDE.md 的要求，泄露声明必须在形式定义、构造、定理陈述、证明中保持一致。当前仅有自然语言论证。
- **修改建议**：要么给出形式化的模拟论证（构造模拟器证明服务器视图可被模拟），要么将 (3.12) 降级为非正式的隐私性讨论，并明确标注其非定理级别的性质。

**M6. [Logic] $\mathsf{MPos}$ 键碰撞的安全影响未在证明中处理**

- **位置**：§3.3 开头段落 + §3.1.3 "服务器侧认证元数据结构"
- **问题**：文中承认不同关系可能生成相同的交叉标签值（$\mathsf{MPos}$ 键碰撞），并建议扩展为多值映射。但命题 3.1 的证明完全忽略了该碰撞事件。如果碰撞发生，$\mathsf{MPos}[\mathsf{xtag}]$ 返回的 $(r, \mathsf{rt}, \sigma)$ 可能属于错误的关系，导致开封验证使用了错误的 Merkle 树。虽然文中声称碰撞概率可忽略，但证明中应当显式引入该坏事件并给出概率界。
- **修改建议**：在证明中增加一个 Game 跳跃（或在 $G_0$ 到 $G_1$ 之间插入），显式定义 $\mathsf{MPos}$ 键碰撞事件 $E_{\mathsf{col}}$，并证明 $\Pr[E_{\mathsf{col}}] \le \mathsf{negl}(\lambda)$（在伪随机群元素或随机预言机模型下）。将该项加入最终的优势界。

## 3. 优先修改建议：如果只允许修改 3 处

**第一优先：C1（$p_2=0$ 的证明缺口）**

这是最严重的技术问题。命题 3.1 是本章的核心安全定理，其证明的正确性直接决定了整个地址绑定机制的安全性基础。True Negative 分支下 $p_2 \neq 0$ 意味着当前证明不完整。修复方案：要么收紧定义 3.1 的胜利条件（排除 $\mathsf{Auth}_{i,j}=\emptyset$ 的关系），要么修改算法 4 的验证逻辑使其在 True Negative 分支下也执行某种形式的地址归属检查，然后重写 $G_2$ 分析。这是"claim stronger than proof"的典型实例。

**第二优先：C3（定义 3.1 的安全实验形式化不充分）**

安全定义是证明的基础。当前定义 3.1 的对手模型、实验流程、关键参数的计算规则均不明确，导致证明的起点就不稳固。修复定义 3.1 也是修复 C1 的前提——只有在实验形式化清晰后，才能准确判断 True Negative 分支应如何处理。

**第三优先：C2（跨章节符号不一致）**

符号不一致直接影响命题 3.2（组合可验证性）的可信度。审稿人在检查组合证明时，如果发现两章的符号体系无法对接，会对整个安全论证的严谨性产生根本性质疑。统一符号体系是使论文通过严格审查的必要条件。
